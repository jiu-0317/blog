
# KV260 커스텀 SPI 슬레이브 코어 — 베어메탈 검증 트러블슈팅 정리

**플랫폼**: Kria KV260 (K26 SOM, Zynq UltraScale+ MPSoC) **구성**: PL에 커스텀 RTL SPI 슬레이브 코어(TOP.v / SPI_slave.v / IR.v / CONTROL.v / FPU / ACC / ACC_R), PS SPI0 마스터 (EMIO 라우팅) **검증 환경**: Vitis 베어메탈 (standalone, psu_cortexa53_0), XSpiPs 드라이버 **최종 결과**: `RESULT = 0x51` — 기대값(1.0×1.0 아홉 개 누산 = 9.0의 E4M3 표현)과 일치, end-to-end 검증 성공

---

## 문제 1. Vitis 에디터에서 `'xspips.h' file not found` 및 대량의 타입 에러

### 증상

- `main.c`에서 `xspips.h`, `XSpiPs`, `u8`, `u16` 등 20여 개의 clang 에러 표시
- 그러나 앱 빌드는 성공

### 원인

- Vitis 에디터의 **clang 인덱서가 BSP include path를 늦게 인식**한 것. 실제 컴파일러(gcc)는 BSP 경로를 정상 참조
- BSP의 `libsrc/spips/src/`에 `xspips.h`가 물리적으로 존재함을 확인

### 해결

- **빌드 성공 여부로 판단** — 에디터 빨간 줄은 무시해도 기능상 문제 없음
- 필요 시 Clean → Build 또는 Vitis 재시작으로 인덱서 갱신

### 교훈

- BSP 헤더가 실제로 없다면 플랫폼 미빌드이거나, Vivado PS 설정에서 SPI0 EMIO enable이 누락된 것 → `libsrc/`에 드라이버 폴더 존재 여부로 판별

## 문제 2. 시리얼 콘솔 — COM 포트 2개 중 어느 것?

### 증상

- KV260 USB 연결 시 장치 관리자에 COM5, COM7 두 개가 잡힘

### 원인

- KV260의 USB-UART 브릿지가 PS UART 두 채널을 각각 가상 COM 포트로 노출 (정상 동작)

### 해결

- 두 포트를 모두 열어보고(115200 8N1) **부팅 로그 / `xil_printf` 출력이 나오는 쪽**이 콘솔
- 이후 같은 포트가 계속 콘솔로 유지됨

## 문제 3. `Unknown command 'connect'`

### 증상

- 터미널에서 `connect` 입력 시 `Unknown command 'connect' - try 'help'`

### 원인

- `connect`는 **XSCT(xsdb) 명령**인데, 입력한 창은 **보드의 U-Boot 콘솔**(`ZynqMP>` 프롬프트)이었음
- 시리얼 터미널 = 보드 출력을 보는 곳, XSCT 콘솔 = JTAG로 보드를 제어하는 곳 — 서로 다른 창

### 해결

- XSCT/xsdb 콘솔(프롬프트 `xsct%` 또는 `xsdb%`)에서 `connect`, `mwr` 등의 명령 수행
- 시리얼 터미널은 `xil_printf` 출력 확인용으로 그대로 유지

## 문제 4. `RESULT = 0x00` — 결과가 항상 0

### 증상

- FSBL 로그와 함께 앱은 정상 실행되고 UART 출력도 나오지만 결과가 `0x00`
- 기대값 계산상 0이 아니어야 함 (W=I=1.0 아홉 개 → 9.0 → E4M3 `0x51`)

### 디버깅 과정 (범위를 반씩 좁히기)

**1단계 — 실행 환경 확인**

- Run 설정의 **Program Device**(= Program FPGA, 비트스트림 다운로드) 체크 확인 → 켜져 있었음
- EMIO 사용 시에도 PL 비트스트림은 반드시 필요 (슬레이브 코어가 PL에 있으므로)

**2단계 — ILA 삽입**

- probe: `emio_spi0_sclk_o`, `emio_spi0_ss_o_n`, `emio_spi0_m_o`(MOSI), `TOP_0_o_miso`, `o_cmd_done`
- **ILA 샘플링 클럭은 반드시 `i_clk`(100MHz PL 클럭)** — 슬레이브가 100MHz로 SPI 신호를 오버샘플링하는 구조이므로, SCLK로 찍으면 내부 동작을 놓침

**3단계 — 1차 캡처 (트리거: SSn Falling `F`)**

- SSn 하강~상승 한 트랜잭션 확인: SCLK 토글 정상, MOSI에 LOAD_W 프레임(0x0700) 패턴 정상
- **`o_cmd_done`이 SSn 상승 직후 High** → 명령이 코어에 도달하고 FSM이 처리 완료
- 결론: **수신(RX) 경로 전체 정상** → 문제는 송신(TX/MISO) 쪽으로 좁혀짐

**4단계 — 2차 캡처 (트리거: `o_miso` Rising `R`)**

- 트리거 성공 — READ 더미 트랜잭션의 하위 바이트 구간에서 MISO에 `01010001` 패턴 출력
- 이는 기대값 **0x51과 정확히 일치** → 코어의 TX 경로(acc_done → tx_load → TBUF → MISO)도 정상

**5단계 — BD 연결 확인**

- `TOP_0/o_miso` → `emio_spi0_m_i` 연결 정상 (마스터 모드 MISO 입력 = `m_i`, MOSI 출력 = `m_o`)
- TOP.v의 TX 패딩 `{8'h00, acc_r_data}` — 결과가 하위 바이트에 실리는 것 확인, SW의 `rx & 0xFF` 판독 위치도 올바름

### 최종 원인

- **하드웨어는 처음부터 정상.** `0x00`이 나온 실행은 **FSBL 자동 플로우에서 PS 초기화(클럭)가 제대로 되지 않았던 상태**의 결과
- 수동 psu_init 플로우로 전환한 이후에는 정상 동작 중이었음 (문제 5 참조)

### 검증 결과

- 시리얼 터미널: `RESULT = 0x51` — 골든 계산값과 일치
- 확인된 것: EMIO 배선, SPI 물리 경로, 16비트 프레임 수신/IR 디코딩/CONTROL FSM, FPU 곱셈, ACC 누산, ACC_R 포맷 변환(E5M7→E4M3), READ 2-트랜잭션 시퀀스, PS 소프트웨어 전부 정상

## 문제 5. Vitis Run 시 ILA 세션 소멸 / 수동 psu_init과 충돌

### 증상

- ILA를 "Waiting for Trigger"로 걸어두고 Vitis Run을 실행하면 ILA 창이 사라짐
- 이전부터 FSBL 자동 플로우로는 PS 클럭이 켜지지 않아 수동 psu_init이 필요했음

### 원인

- Vitis Run 설정의 **Reset Entire System + Program Device + Init With FSBL**이 실행 시:
    1. 시스템 전체 리셋 (PL 포함)
    2. 비트스트림 재다운로드
- 이 과정에서 **수동으로 해둔 psu_init도, arm해둔 ILA 세션도 전부 무효화**됨
- 즉 수동 초기화 플로우와 Vitis 자동 플로우가 서로 판을 엎는 충돌

### 해결 — 전 과정을 xsdb로 통일

```tcl
# 1. 비트스트림 로드 + PS 초기화
fpga -f <경로>/design_1_wrapper.bit
targets -set -nocase -filter {name =~ "*PSU*"}
source <경로>/psu_init.tcl
psu_init
psu_ps_pl_isolation_removal
psu_ps_pl_reset_config

# 2. ★ 여기서 멈추고 → Vivado HW Manager에서 ILA arm (트리거 설정 + Run Trigger)

# 3. ILA arm 후 이어서 앱 다운로드/실행
targets -set -filter {name =~ "*A53*#0"}
rst -processor
dow <경로>/<app>.elf
con
```

- 핵심: **비트스트림 로드가 끝난 뒤 → ILA arm → 그 다음 `con`** 순서. 리프로그램 이후에 arm하므로 세션이 날아가지 않음
- 대안: Vitis를 계속 쓰려면 Run 설정에서 Reset Entire System / Program Device / Init With FSBL을 끄고 Reset APU만 사용 (수동 초기화를 존중하는 구성)

### 남은 과제

- FSBL 자동 플로우가 PS를 제대로 초기화하지 못하는 근본 원인 미해결 — 플랫폼이 참조하는 XSA가 구버전이라 FSBL의 psu_init이 현재 하드웨어와 불일치할 가능성이 유력. **최신 XSA로 플랫폼 업데이트 후 재빌드** 필요 (검증 완료 후 정리 예정)

## 참고: 확정된 SW/HW 인터페이스 사양

### PS SPI 마스터 설정 (XSpiPs)

|항목|값|근거|
|---|---|---|
|모드|Mode 0 (CPOL=0, CPHA=0)|슬레이브: rising에서 MOSI 샘플, falling에서 MISO shift|
|옵션|`XSPIPS_MASTER_OPTION \| XSPIPS_FORCE_SSELECT_OPTION`|PolledTransfer 동안 SS 유지 → 2바이트 = 1프레임|
|SCLK|6.25MHz (`XSPIPS_CLK_PRESCALE_32`)|슬레이브 2-FF 동기화기 한계 12.5MHz(f_clk/8)에 마진 확보|
|전송 단위|2바이트 (MSB 먼저, buf[0]=frame[15:8])|16비트 프레임, SSn 상승에서 rx_done|

### 프레임 포맷

```
cmd[15:13] | data[12:5] | addr[4:1] | mode[0]
CMD: 0=LOAD_W, 1=LOAD_I, 2=COMPUTE, 3=ACC, 4=READ_RESULT
mode: 0=E4M3, 1=E5M2
```

### READ 시퀀스 (2 트랜잭션)

1. `CMD_READ_RESULT` 전송 → SSn 상승 후 FSM이 tx_load 수행, 다음 SSn 하강에서 TBUF 로드
2. 더미 2바이트 전송 → MISO로 결과 수신, **하위 바이트**에 8비트 결과 (`{8'h00, acc_r_data}`)

### ILA 사용 수칙

- 샘플링 클럭 = `i_clk`(100MHz), SPI 신호는 probe로만
- 트리거: 트랜잭션 관찰 시 SSn `F`(Falling), TX 확인 시 `o_miso` `R`(Rising)
- Trigger position은 창 앞쪽(~100/1024)으로 → 트리거 이후 프레임 전체 확보
- 6.25MHz 16비트 프레임 ≈ 2.56µs ≈ 100MHz 기준 256샘플 → depth 1024면 충분

### 검증된 골든 케이스

- 입력: W = I = `0x38` (E4M3, 1.0) × 9개
- 파이프라인: IR에서 E5M3 변환(exp+8) → FPU 1.0×1.0=1.0 → ACC 9회 누산 = 9.0 (E5M7 `0_10010_0010000`) → ACC_R에서 E4M3 변환(exp−8) = `0_1010_001`
- 기대/실측: **0x51 / 0x51 일치**
