# Setup Time (tsu)

Setup time은 클럭 엣지가 도착하기 "전에" 데이터가 안정적으로 유지되어야 하는 최소 시간.

예를 들어 rising edge 트리거 FF라면, 클럭이 올라가기 전 tsu 동안 데이터 입력(D)이 변하면 안된다. 이걸 위반하면 setup violation이 발생하고, FF가 데이터를 제대로 래치하지 못해서 metastability 상태에 빠질 수 있다.

# Hold Time (th)

Hold time은 클럭 엣지가 도착한 "후에" 데이터가 안정적으로 유지되어야 하는 최소 시간.

클럭 엣지 이후에도 th 동안은 데이터가 바뀌면 안된다. 이걸 위반하면 hold violation이 발생한다.


# Slack 

## Timing Slack
Slack은 타이밍 여유를 나타내는 값.

Setup slack의 경우, 데이터가 실제로 도착한 시점과 setup time 데드라인 사이의 차이야. 식으로 쓰면:
- Setup Slack = (Required Arrival Time) − (Actual Arrival Time)

Hold slack도 비슷하게:
- Hold Slack = (Actual Arrival Time) − (Required Arrival Time)

두 경우 모두 slack이 양수(positive)면 타이밍을 만족하는 거고, 음수(negative)면 violation이야. STA(Static Timing Analysis) 도구에서 가장 중요하게 보는 지표 중 하나지.


# Slew
슬루(slew)는 신호가 한 전압 레벨에서 다른 전압 레벨로 전환되는 데 걸리는 시간입니다. transition time이라고도 합니다.

예를 들어 0V에서 5V(VDD)로 올라가는 rising 신호가 있을 때, 보통 VDD의 20%~80% 구간(또는 10%~90%)을 지나는 데 걸리는 시간을 슬루라고 합니다. falling도 마찬가지로 80%→20% 구간의 시간입니다.


# False path
회로의 네트리스트 상에는 존재하지만, 실제 동작 시에는 **신호가 절대로 통과할 수 없는 타이밍 경로**를 의미한다. 

**왜 생기는가?**
STA 툴(예: Innovus, PrimeTime 등)은 회로의 모든 가능한 조합 경로를 **구조적으로** 탐색합니다. 그런데 회로의 **논리적 조건** 때문에 특정 입력 조합이 동시에 활성화될 수 없는 경우가 있어요. 툴은 이걸 모르기 때문에, 실제로는 활성화되지 않는 경로도 "위반(violation)"으로 잡을 수 있습니다.

예를 들어
1. MUX에는 구조적으로 A→출력, B→출력 두 경로가 존재
2. STA 툴은 둘 다 "신호가 지나갈 수 있는 경로"로 보고, 각각의 delay를 계산
3. 이때 B→출력 경로의 delay가 클럭 주기를 초과하면 → 타이밍 위반으로 보고

문제는, **실제 회로 동작에서 sel이 항상 0으로 고정되는 설계**라면 B 경로로는 신호가 절대 전파되지 않는다는 것. 그런데 STA 툴은 이런 **논리적 조건을 모르기 때문에** B 경로도 위반으로 잡아버리는 것이다. 

**실무에서 어떻게 처리하나?**
STA 툴에서 `set_false_path` 같은 SDC 제약 조건을 사용해서, "이 경로는 분석하지 마라"고 지정합니다.
```tcl
set_false_path -from [get_pins mux/B] -to [get_pins reg/D]
```
이렇게 하면 툴이 해당 경로를 타이밍 분석에서 제외하므로, 불필요한 위반 보고가 사라지고, 합성/P&R 툴이 진짜 critical path에 최적화를 집중할 수 있게 됩니다.

---

다음은 클로드가 알려주는 false path를 찾아내고 처리하는 방법이다. 

실무에서는 **두 가지 접근**이 섞여서 쓰입니다.

**1. 설계자가 아키텍처 레벨에서 미리 아는 경우**

가장 흔한 케이스예요. 설계자가 자기 회로를 알기 때문에 "이 경로는 논리적으로 불가능하다"는 걸 설계 단계에서 이미 파악하고 있습니다. 대표적인 예시들:

- **클럭 도메인 크로싱(CDC)**: 서로 다른 클럭 도메인 사이의 경로는 동기화 로직으로 처리하므로, 단일 사이클 타이밍 분석이 무의미 → false path 지정
- **MUX 기반 모드 선택**: 테스트 모드 / 정상 모드처럼, 동시에 활성화되지 않는 경로
- **정적 설정 레지스터**: 부팅 시 한 번 쓰고 동작 중에는 변하지 않는 config 레지스터에서 나가는 경로

이런 건 SDC 파일에 미리 `set_false_path`를 작성해두는 게 일반적이에요.

**2. 타이밍 리포트에서 발견하는 경우**

STA 돌린 후 타이밍 위반 리포트를 보다가, worst path가 "이건 실제로 활성화될 수 없는데?" 싶은 경로인 경우가 있어요. 이때 설계자가 해당 경로의 논리 조건을 추적해서 false path 여부를 판단합니다.

**자동으로 찾아주는 방법도 있긴 해요:**
일부 EDA 툴에서는 **자동 false path 탐지** 기능을 제공합니다. 예를 들어 Synopsys PrimeTime의 경우 `report_timing -true`나 ATPG 기반 path sensitization 분석으로, 구조적 경로가 실제로 sensitize 가능한지(신호가 실제로 전파될 수 있는지) 검증할 수 있어요. 다만 이건 연산 비용이 크기 때문에, 전체 경로에 대해 돌리기보다는 의심되는 경로에 대해 선택적으로 쓰는 편입니다.

**실무의 현실적인 흐름은 이렇습니다:**
설계자가 아키텍처를 기반으로 SDC에 false path를 미리 선언해두고 → STA를 돌리고 → 리포트에서 여전히 이상한 위반이 보이면 → 해당 경로를 분석해서 추가로 false path를 지정하는, **반복적인 과정**이에요.

결국 핵심은, false path는 **회로의 논리적 동작을 이해하는 설계자의 판단**이 필수라는 점이에요. 툴이 구조만 보고 자동으로 완벽하게 걸러내기는 어렵기 때문에, 설계자의 회로 이해도가 타이밍 분석의 정확성을 좌우합니다.
